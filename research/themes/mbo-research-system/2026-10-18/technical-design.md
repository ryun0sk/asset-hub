# MBOリサーチシステムの技術設計

現行案は[無料版の技術設計](free-technical-design.md)。以下は有料データも比較した当初案の仕様として残している。

設計日：2026-10-18（日本時間）。[当初の実装プラン](initial-paid-plan.md)を実装単位へ分解した提案。以下のパス・CLI・API・スキーマは今後作る仕様であり、今回実装したものではない。

## 1 構成と処理量

個人利用のバッチ処理として、Pythonの収集・計算処理、SQLiteの状態管理、原資料ファイル、日付別JSON、既存Asset Hubの表示を使う。最初の設計容量は普通株5,000証券、週20社の機械による詳細調査、そのうち毎週5〜10社の人手確認を仮置きする。上場社数の実測値ではなく、容量試験の条件である。

全社の一次抽出は定型データの処理で完了させる。長い文章のLLM処理は候補と変更資料に限り、書類ハッシュ・抽出方式・モデル・プロンプト版が同じなら保存済み結果を再利用する。APIのV2・ページング・レート制限は提供元の現行仕様に合わせる。[J-Quants案内](https://jpx-jquants.com/ja/spec)、[レート制限](https://jpx-jquants.com/ja/spec/rate-limits)

処理を `collect → normalize → extract → validate → screen → value → export` に分ける。過去検証用の `backtest` は同じ特徴量・計算器を使い、情報を利用できる時点の制約を追加する。収集失敗と「資料がない」は別状態で記録する。

## 2 データ取得の契約

下表は当初のJ-Quantsを中心とする取得案。同日の追加調査で、バフェット・コードにも詳細財務・大株主・会社資料の取得経路を確認したため、経路の最終選定では[同サービスの適合性](buffett-code-assessment.md)と比較する。表の経路を一式契約することを前提にしない。

| 必要データ | 優先経路 | 補完と品質確認 |
|---|---|---|
| 銘柄・価格・取引日 | J-Quants V2の銘柄一覧、日足、取引カレンダー | 過去の母集団、上場廃止、分割、商品区分を試験。価格の調整方法を固定 |
| 財務の一次抽出 | J-Quants財務サマリー | 提出・公表時点、訂正、連結/単体、年度/累計を識別 |
| 詳細財務と注記 | EDINET XBRL/CSV、有報、会社決算資料 | Standardには詳細BS/PL/CFがないため、CF・借入・リース・資産の不足を原本で補う |
| 大株主等 | Standardの株主関連API、EDINET原本 | 経営陣・親族・資産管理会社の関係を証拠付き名寄せ。信託を実質所有者としない |
| 適時開示 | 初期は会社IR、必要ならJ-Quants TDnetアドオン | 取得日時と訂正・取消の関係を記録し、対象期間・資料の取り漏れを監査 |
| 具体的な検討第一報 | 公式発表、出典を確認できる報道 | 当初は人が確定。不明な第一報を正式発表日と同一視しない |
| MBO台帳 | 正式発表・公開買付資料・結果・上場廃止資料 | 管理者の関与、再出資、取引種別、初回公表と成立を別に確認 |

EDINETはAPIキーが必要。ブラウザから直接取得する構成にはせず、サーバー側の収集処理に限る。書類一覧の日付指定と書類別の閲覧可能期間は別の制約である。[公式API仕様](https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/download/ESE140206.pdf)

J-Quants TDnetの現仕様では、訂正・削除をインデックスの状態フラグだけで判定できない。書類本文の訂正・取消情報、新旧IDの対応、取得済みハッシュを照合し、確認できない有効性を保留にする。[TDnet仕様の留意点](https://jpx-jquants.com/ja/spec/td-list)

J-Quants政策保有株式APIにはLLMによる修正の注記がある。構造化データも無条件に正解とみなさず、評価に影響する金額と資産の範囲は原本へ戻る。[政策保有株式API](https://jpx-jquants.com/ja/spec/edinet-cross-shareholdings)

## 3 保存モデル

| テーブル | 主な項目 | 目的 |
|---|---|---|
| issuer / security | issuer_id、security_id、EDINETコード、法人番号、証券種別 | 会社と証券を分離。コード再利用・種類株・合併に対応 |
| identifier_history | ID種別、コード、valid_from、valid_to、根拠 | 英字を含むコードを文字列として保持。表示名と恒久IDを分ける |
| universe_snapshot | 基準日時、市場、在籍証券、対象/除外、除外理由 | 生存企業だけに偏らない母集団を保存 |
| document / document_version | 提供元ID、URL、public_at、observed_at、hash、原本パス、訂正/取下げ関係 | 原本と版を上書きせず保存 |
| fact / evidence | 指標名、値、通貨、単位、会計期間、連結/単体、実績/会社予想/外部予想、ページ/項目位置 | 異なる定義の数値を混ぜない |
| ownership / ownership_relation | 基準日、公開日時、名義、持分、議決権、関係の根拠、確認者 | 名寄せの推測と確認済みの関係を分離 |
| event / event_status | イベントID、分類、第一報、正式公表、成立、撤回、買付価格履歴、根拠 | 発表予測と成立結果を分離 |
| feature_snapshot | 基準日時、定義版、入力fact IDs、値、欠測理由、計算方式 | 将来値の混入を検査できる特徴量 |
| valuation_scenario | シナリオID、仮定、DCF、株数、LBO条件、結果、感応度、入力ID | 独自シナリオを実績と分離 |
| review / override | 対象、旧値、新値、理由、根拠、確認者、確認日時 | 人手の修正を履歴として残す |
| run_manifest | 実行ID、入力hash、コード/ルール/モデル/プロンプト版、開始終了、費用、成功状態 | 再現と費用監査 |

各数値の状態は `verified / pending / conflicting / missing / not_applicable` 等の列挙値で持つ。欠測理由は未開示、未取得、抽出失敗、定義不一致、鮮度不足を区別する。「データなし」を現金ゼロや持分ゼロに変換しない。

## 4 時点と履歴の扱い

各書類・抽出値に少なくとも次を持たせる。

- `period_end`：財務等の対象期末。
- `public_at`：この版が公表された日時。日付のみの場合は時刻精度を別記。
- `provider_available_at`：配信経路での利用開始日時。分からなければ欠測。
- `observed_at`：収集処理が実際に初取得した日時。
- `ready_at`：抽出と必要な検証を終えた日時。
- `supersedes / withdrawn_at`：訂正・取消と有効性の関係。

実運用の特徴量は `max(public_at, provider_available_atが判明していればその値, observed_at, ready_at)` 以降に利用する。公表時刻不明の資料は、当日寄付きの判断に使わず、保守的に翌営業日からとする。後日初取得した資料のobserved_atを過去へ戻さない。

過去の資料を今から取得するバックテストでは、当時の版と公表日時が検証できる場合に限って「事後再構成」として使う。現在の収集能力を当時も持っていたという仮定や、配信遅延・抽出時間の仮定を明記する。訂正前の版を復元できない指標は除外し、どの程度の母集団・特徴量が落ちたかを出す。EDINETの訂正・書類情報修正・不開示は別の処理なので、IDだけでは原本の不変性を保証できない。[EDINET FAQ](https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/WZEK0090_001.html)

再抽出で解釈が変わる場合も新しい抽出版を作る。原資料版、抽出版、特徴量版、評価ルール版を独立して残す。入力・コード・仮定を固定した数値計算は再現可能にする一方、LLMの再呼出しで同じ文章になることは保証せず、採用した応答を保存して再生する。

## 5 計算仕様

初期は日本円を標準通貨とする。外貨項目は換算日と為替出典を付け、同一計算内で混在させない。株価と発行済株数は同一日の分割基準にそろえ、自己株式と希薄化の扱いを明示する。

```text
基本時価総額 = 未調整株価 × その日基準の（発行済株数 − 自己株式）
非借入FCFの基本式 = EBIT ×（1 − 税率）+ 減価償却 − 設備投資 − 運転資本増加
DCF事業価値 = 将来の非借入FCFの現在価値合計 + 継続価値の現在価値
株主価値 = 事業価値 + 重複しない非事業資産の税引後価値 − 有利子負債等
1株価値 = 株主価値 / 定義した希薄化後株数
基準価値に対する割安率 = 1 − 現在株価 / 基準1株価値
弱気価値までの下落幅 = 弱気1株価値 / 現在株価 − 1
```

非借入FCFは資金提供者全体に帰属するFCFFとし、利払い前の営業利益から作り、実効税・リース等を調整する。割引率は資金調達全体に対応するWACCを使い、利払い後の株主CFを同じ式に混ぜない。現金、非事業資産、リース、非支配持分、年金等の帰属と処理を別表で照合する。倍率比較のEV、EBITDA、リース基準を同業間で統一する。

DCFは弱気・基準・強気とし、割引率・長期成長率・利益率・投資額を感応度表示する。永久成長式で長期成長率が割引率以上（g >= r）の場合、矛盾した会計期間、重要項目の欠測では値を出さない。赤字や循環産業に通常のPERを機械適用しない。価格評価に欠かせない項目を埋めるための仮定は、確認済み事実と別欄に置く。

LBOモデルは5年保有を初期の独自シナリオとし、期間を変更可能にする。資金使途と調達の一致、借入返済後CF、最低現金、残債、出口株主価値、スポンサーIRRを計算する。借入条件・出口倍率・要求IRRは出典のある条件か独自仮定かを区別する。株主への買収対価と、借換え・手数料を含む総資金需要を取り違えない。持分継続による必要現金の減少と、経済的な企業価値を分ける。

想定買収価格を変えながら、資金と返済と要求収益率の条件を満たす範囲を探索する。条件を満たす価格がない場合は「成立範囲なし」、重要データがない場合は「計算保留」。買付プレミアムの過去平均を強制的な目標株価にしない。

## 6 LLMの境界と出力

LLMは資料中に明示された事実を構造化し、候補の理由と反証を整理する。数値の集計・割引計算・順位算出はコードで行う。抜き出した項目には原文位置、単位、対象期間、出典版、抽出方式を必須にする。数値が原本と一致しない場合は保留する。

資料内の指示、リンク、コードは外部データとして扱い、実行しない。抽出処理にログイン情報や外部操作権限を渡さない。ZIP・PDF・HTMLは許可した処理器に限り、パス逸脱・異常サイズ・危険な埋込内容を避ける。引用は根拠確認に必要な短い範囲と位置情報を保存し、本文を丸ごと画面へ再配布する設計にしない。

過去検証では「社長高齢なので承継課題が強い」などのAI解釈を特徴量にしない。公開資料に明示された承継方針等を、固定した定義で確認した場合だけ利用する。企業名を隠す方法だけでは、モデルが知る過去結果の混入を防げたとは判断しない。

## 7 ファイルと画面への出力

今後の実装配置案は以下。原資料や契約データ、SQLiteはGit対象外に置き、契約データを公開リポジトリへ入れない。

```text
backend/mbo/                       # 収集、正規化、特徴量、価格計算、検証
data/private/mbo/raw/               # 原本と取得履歴
data/private/mbo/state.sqlite       # ローカルの状態
data/private/mbo/runs/              # 実行台帳と凍結した出力
research/themes/mbo-screen/YYYY-MM-DD/
  README.md                        # 時点と対象範囲
  report.md                        # 確認済みの週次メモ
  index.html                       # 候補と詳細を読む画面
  snapshot.json                    # 保存が許容される表示用成果物のみ
```

ライセンス確認前は、取得した有償データ・派生値をresearch配下へ書き出さない。研究資料を画像へ同梱する現行配信方式と整合するかも確認する。許可範囲に応じて、データ出力を本人用の非公開バケットと認証済みGET配信に切り替える。

当初は静的JSONを既存の調査表示から読む方式を優先する。動的な配信が必要になった場合に限り、`GET /api/mbo/snapshots`、`GET /api/mbo/candidates?as_of=...`、`GET /api/mbo/companies/{id}?as_of=...` を追加する。書込HTTP APIは初期要件にしない。

候補の出力項目には、基準日時、企業ID、取引状態、抽出順位、条件別根拠、単独継続価値、資金試算、欠測、確認日、計算版を含める。確率を校正するまで `mbo_probability_12m/24m` はnullとし、理由を「未検証」とする。画面ではnullを0%に変換しない。

## 8 検証と受入条件

12/24か月以内の初回正式MBO公表をラベルとし、成立・撤回・競合取引・打切りは別に管理する。公開検討報道後の企業は未発見候補の対象から外す。報道履歴不明は不明として残す。

案件台帳から市場合計の基準率を推定する。検証は時系列で分割し、ラベル期間が評価期間へ重なる学習データを除く。チューニング用と最後に使う評価期間を分け、企業単位の分離でも確認する。毎月同じ会社を出した結果を別々の成功案件として加算しない。信頼区間は企業と時間の依存を考慮する。

初期に仮置きする受入条件は次のとおり。第1週の試験で測定方法を確定し、成績評価を始める前に固定する。

| 段階 | 条件案 | 満たさない場合 |
|---|---|---|
| 調査票 | 表示する主要な主張に出典が100%付く。重要数値を人が照合し、未解決の矛盾がある値を確定表示しない | 抽出・定義を修正。自動判定を保留 |
| MVP | 未来情報を意図的に混ぜた試験を全件検出。単位・分割・連結・訂正の試験が通る。再実行で重複せず、同じ計算値を再現 | 機能拡張前に修正 |
| 調査の運用 | 主要項目の確認を含む深掘りが1社30分以内を目標。超過理由・未確認項目・修正率を記録 | 取得経路や対象範囲を見直す |
| 拡張判断 | precision@20のliftが基準モデルの1.5倍以上を目標として事前設定し、十分な案件数・不確実性・先行日数も評価 | 点推定だけで採用せず、標本不足なら判断保留。改善しない場合はルール版を維持 |
| 確率表示 | 時系列評価と前向き評価で校正を確認し、12/24か月ラベルの成熟・打切りを処理できる | 順位と根拠の表示を継続 |

1.5倍や30分は達成実績ではない。結果に合わせて合格基準を変えない。候補発見が改善しても売買収益が改善したとは判断せず、投資シミュレーションの成績を別に出す。

## 9 運用と費用制御

単一の実行ロックとSQLiteトランザクションで同時実行を避ける。収集・抽出の主キーは提供元ID・原本hash・処理版。出力は一時領域で完成させ、検証成功後に原子的に切り替える。途中で失敗した版を最新扱いしない。

タイムアウト・再試行・ページング・取得上限を設定し、直近日付の再照合と、過去の訂正・取消の確認を分ける。前回成功版の時点、情報の古さ、欠測率、処理待ち件数、モデル費用、原本照合での修正率を記録する。

LLMには月額上限、1実行上限、資料数上限を設定する。予約した最大費用を含めた残額が次の処理に足りなければ停止する。価格を確認できないモデルは自動運用に入れない。上限到達後は定型データ処理と既存画面の閲覧を継続し、AI未処理を表示する。

認証情報を原本、ログ、URL一覧、画面JSONへ残さない。EDINETのクエリに含まれるキー等もマスクする。サイトログイン・GCP再認証が必要になったときは共通site-login skillを使い、OTP等は本人へ引き継ぐ。今回の設計では認証情報を取得しない。

定期実行や通知は実装段階で明示的に設定する。本人用の更新通知は重要な変化に限る設計とし、この計画を保存しただけでは自動化や有料契約を開始しない。
